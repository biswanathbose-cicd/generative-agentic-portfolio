# 01 - Multi-agent retail support assistant

A small but complete agentic system: guardrails -> LLM router -> specialist agents that call traced tools -> facts-only answer
writer -> grounding check -> JSONL log. It runs with **no API key** (deterministic rule-based backend) and swaps to a real model
with environment variables.

```
user text -> input guardrails (PII redaction, injection screen)
          -> router (LLM, JSON-only intent)
          -> order_agent | returns_agent | product_agent | handoff_agent | out-of-scope refusal
                 \-> ToolRegistry: get_order_status, check_return_eligibility, initiate_return,
                                   search_products (hybrid TF-IDF RAG), create_handoff_ticket
          -> answer writer (LLM, "use only these facts")
          -> output guardrails (prices / order ids / action claims must be backed by tool results)
```

## Design choices worth knowing
- **Tools are traced and step-capped** (`ToolRegistry.max_steps`) so runaway loops are impossible and evaluation can score tool-call accuracy.
- **`initiate_return` deliberately does not re-check policy** (like many real backends). The *agent* must call `check_return_eligibility` first;
  the baseline doesn't, and the eval framework measures the resulting policy violations.
- **Guardrails are layered:** PII is redacted *before* routing and logging; replies are rejected if they state a price or order number no tool returned.
- **One code path for both backends:** prompts live in `prompts.py` and are sent verbatim to real LLMs; the rule-based backend keys off a `TASK=` header.
- **Retrieval:** word TF-IDF blended with character-n-gram TF-IDF (typo-robust), with price filtering.

## Versions (feature flags in `config.py`)
| flag | `v1_baseline` | `v2_improved` | `v2.1_fuzzy_fix` |

| fuzzy routing / typo repair | no | yes | yes, <=1 edit + corroboration |

## Run
```bash
pip install -r requirements.txt
python scripts/chat_cli.py --trace                 # interactive; try: "where is my order WM-10003?"
python -m unittest discover -s tests -v            # 25 pass, 1 skipped without FastAPI
uvicorn support_agent.api:app --app-dir src        # HTTP: POST /chat, POST /feedback, GET /metrics, GET /health
docker build -t support-agent . && docker run -p 8000:8000 support-agent
```
Real model backends: `LLM_PROVIDER=anthropic ANTHROPIC_API_KEY=... [ANTHROPIC_MODEL=...]` or
`LLM_PROVIDER=openai OPENAI_API_KEY=... [OPENAI_BASE_URL=...]`. Then re-run `02-eval-framework/run_eval.py` to compare against the offline numbers.

## Limitations (please read)
- The default "LLM" is rules. It proves the orchestration, guardrails and evaluation plumbing; it says nothing about LLM answer quality.
- `AnthropicLLM` / `OpenAICompatLLM` (stdlib HTTP), `api.py` (FastAPI), the Dockerfile and `.github/workflows/ci.yml` were **not run** where this was built.
  API coverage is `ApiTests` in `tests/test_assistant.py`; it is skipped when FastAPI/httpx are absent.
- **Known guardrail gap, found by the held-out eval and intentionally not patched here:** the assistant's PII regex misses phone numbers written as
  `(555) 123-4567`, and its injection patterns miss paraphrases ("Forget everything you were told..."). Project 4's redactor already handles the phone format.
  The right next step is to fix, then re-measure on a *fresh* split, not the one that exposed it.
- Data (120 products, 300 orders) is generated by `data.py`; `REFERENCE_TODAY` is fixed so runs are reproducible.
